# 机房风扇调速控制系统

校企合作课程-软件架构模型与设计（华为设计模式专题）：**单例、观察者、策略**三种经典设计模式在真实后端工程中的落地。

一个面向机房拓扑的风扇调速与温度告警控制系统：两块风扇扩展板（槽位 90、91）负责散热，14 块业务板（槽位 1–14）承载温度仿真；系统每秒采集一次全部业务板温度，自动决策风扇三档转速（低速 / 中速 / 高速），温度越过告警线时异步记录告警。

服务端口 8090，生产数据库 MySQL 8（Docker Compose 一键启动），自动化测试使用内嵌内存数据库，无需任何外部依赖。

## 一、快速启动

### 1. 初始化数据库

两种方式二选一。

#### 方式 A：Docker Compose（推荐，零额外依赖）

确保 Docker Desktop 已启动（Windows 下托盘图标为绿色）：

```powershell
cd e:\fan-control-system

# 拉起 MySQL 容器，首次启动时自动执行 schema-mysql.sql 建表
docker compose up -d

# 等待约 15 秒，健康检查通过（STATUS healthy）
docker compose ps

# 验证库表已就绪（可选，-h localhost 强制走 TCP 避免容器内 socket 路径问题）
docker compose exec mysql mysql -h localhost -uroot -proot -e "USE fan_control; SHOW TABLES;"
# 预期输出三张表：fan_board / business_board / alarm_record
```

编排文件已预设 MySQL 8.0 镜像、账号密码 root/root、自动建库 `fan_control`、挂载建表脚本到容器初始化目录、数据持久化到命名卷（重建容器不丢数据）。

#### 方式 B：本地 MySQL 手动初始化

如果本机已有 MySQL 8+ 且不想用 Docker：

```powershell
# 1) 登录 mysql 客户端
mysql -uroot -p          # 输入你本地 MySQL 的 root 密码

# 2) 在 mysql shell 里执行以下命令（或把两条 source 合并成一条）
CREATE DATABASE IF NOT EXISTS fan_control DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci;
source e:/fan-control-system/src/main/resources/schema-mysql.sql;

# 3) 验证
USE fan_control; SHOW TABLES;

# 4) 退出
exit
```

然后把 `application.yml` 里的 datasource URL 和账号密码改成你本地 MySQL 的实际值（默认 root/root/localhost:3306/fan_control，能直接对上就不用改）。



### 2. 启动应用

```powershell
cd e:\fan-control-system
mvn spring-boot:run
```

应用默认连接本机 3306 端口的 `fan_control` 库，启动时自动建表并播种初始板卡（2 块风扇板 + 14 块业务板，表中已有数据时不会重复播种）。

### 3. 冒烟验证

**手动模式升温 → 切自动风扇自动调速 → 切回手动恢复控制权**。

**第一步：启动，先别切自动**。跑实时温度监控面板（Ctrl+C 退出）：

```powershell
while($true) { Clear-Host; $b = Invoke-RestMethod "http://localhost:8090/api/business-boards"; $b | Select-Object slot, @{N='温度';E={[math]::Round($_.temperature,1)}} | Format-Table -AutoSize; Write-Host "Ctrl+C 退出"; Start-Sleep 1 }
```

观察：风扇板默认 **LOW + MANUAL**，降温能力很弱（LOW 每秒只减 0~0.1℃），但业务板每秒 +0~0.5℃ 自然发热 → 温度净上升，很快就会冲到告警阈值。

**第二步：看风扇板初始状态，顺手试手动调速**：

```powershell
# 当前状态（预期两块都是 LOW + MANUAL）
Invoke-RestMethod "http://localhost:8090/api/fan-boards" | Format-Table -AutoSize

# 91 号板是 MANUAL 模式，可以直接调到 HIGH 验证手动路径通
Invoke-RestMethod -Uri "http://localhost:8090/api/fan-boards/91/speed" -Method POST -ContentType "application/json" -Body '{"speed":"HIGH"}'

# 立刻切回 LOW，保持降温能力弱，让温度继续自然上升
Invoke-RestMethod -Uri "http://localhost:8090/api/fan-boards/91/speed" -Method POST -ContentType "application/json" -Body '{"speed":"LOW"}'
```

两块风扇板初始都是 `slot=90,91 / speed=LOW / mode=MANUAL`。手动调速的验证点只是"MANUAL 模式能直接改档位、不报错"，改完切回 LOW 保证降温能力不干扰后续温度上升观察。

**第三步：等温度冲上去后切自动**。监控面板里看到温度普遍 > 35℃ 时（大概 1~2 分钟），执行：

```powershell
# 两块都切自动
Invoke-RestMethod -Uri "http://localhost:8090/api/fan-boards/90/mode" -Method POST -ContentType "application/json" -Body '{"mode":"AUTOMATIC"}'
Invoke-RestMethod -Uri "http://localhost:8090/api/fan-boards/91/mode" -Method POST -ContentType "application/json" -Body '{"mode":"AUTOMATIC"}'
```

监控面板里立刻能看到：风扇板根据温度自动升档（MEDIUM 或 HIGH），温度上升放缓甚至开始下降。

**第四步：验证互斥语义——自动模式下禁止手动调速**：

```powershell
curl.exe -s -X POST http://localhost:8090/api/fan-boards/90/speed -H "Content-Type: application/json" -d '{"speed":"HIGH"}'
# 预期 409 冲突："风扇板 90 当前为 AUTOMATIC 模式，不能手工调速"
```

**第五步：切回手动，重新拿回控制权**：

```powershell
# 90 号板切回 MANUAL
Invoke-RestMethod -Uri "http://localhost:8090/api/fan-boards/90/mode" -Method POST -ContentType "application/json" -Body '{"mode":"MANUAL"}'

# 再试手动调速——这次成功（上一步 AUTOMATIC 模式下会返回 409）
Invoke-RestMethod -Uri "http://localhost:8090/api/fan-boards/90/speed" -Method POST -ContentType "application/json" -Body '{"speed":"HIGH"}'
# 预期 200 返回：speed=HIGH, mode=MANUAL
```

模式切换是双向任意的：MANUAL ↔ AUTOMATIC 不设单向锁，控制权的唯一约束是"**当前为 AUTOMATIC 时禁止手动调速**"，一旦切回 MANUAL 就立即解除。

**第六步：健康检查**：

```powershell
curl.exe -s http://localhost:8090/actuator/health
# 预期 {"status":"UP"}
```

### 4. 运行测试（可选）

```powershell
mvn test
```

25 个用例覆盖策略逻辑、仿真边界、服务层并发语义、接口错误码、持久层 SQL 和整体装配；测试自动使用一次性内存数据库，不需要启动 Docker 或 MySQL。

### 运行参数调整

告警阈值、控制周期长度、调度开关均为外部化配置，在 `application.yml` 中修改后重启生效，无需改动代码：

- `fancontrol.tick.enabled`：是否开启每秒自动控制（调试时可关闭）
- `fancontrol.tick.interval-ms`：控制周期间隔，默认 1000 毫秒
- `fancontrol.alarm.threshold`：告警温度阈值，默认 75℃

## 二、系统架构

### 分层结构

系统采用经典的分层架构，外部请求与内部定时调度两条入口最终汇聚到同一个主控板服务：

```
  HTTP 请求 ──→ 接口层（参数校验、统一错误响应）
                          │
  每秒定时 ──→ 调度器  ──→ 主控板（全局单例）
                          │
            ┌─────────────┼──────────────┐
            ▼             ▼              ▼
        持久化层       告警事件        调速策略
      （MySQL）     （异步订阅落库）   （可替换规则）
```

- **接口层**：对外暴露 REST 接口，负责请求参数校验和错误语义转换。业务异常不直接抛给调用方，而是统一翻译为 HTTP 状态码——板卡不存在返回 404，自动模式下的非法手动操作返回 409，参数或枚举值非法返回 400，响应体结构全局一致。
- **主控板**：系统的核心。手动调速、模式切换和每秒自动控制全部经由它处理，板卡状态的读写规则集中在这一处，保证同一时刻只有一套控制逻辑在生效。
- **调度器**：以固定每秒一次的频率驱动主控板执行一轮完整控制周期，运行在独立的调度线程池上；单轮任务内部串行执行，任何一轮内部出错只记录日志，不会导致后续调度终止。
- **调速策略**：档位决策被抽象为独立角色，主控板只依赖"给定全部业务板温度、返回一个目标档位"这一约定，不关心规则细节。
- **告警事件**：主控板发现温度越线时只发布一个告警事件，由独立的订阅者异步写入数据库。发事件的一方不关心有多少订阅者、订阅者做什么、是否成功。
- **持久化层**：板卡状态、温度、告警记录全部落 MySQL，应用重启后状态可恢复；数据访问接口与 SQL 映射文件分离，复杂查询的 SQL 直观可见、便于审查。

### 技术选型

| 领域 | 选型与理由 |
|---|---|
| 语言与框架 | Java 17 + Spring Boot 3。框架提供容器单例、声明式调度、事件发布订阅、参数校验、统一异常处理等基础设施，使设计模式的意图直接体现在结构上，而不是淹没在样板代码里 |
| 持久化 | MyBatis + MySQL 8。SQL 手工编写、映射关系透明，便于针对性地写出"带业务条件的更新"语句；板卡状态与告警历史持久化，重启不丢失 |
| 调度与异步 | 框架内置任务调度器，使用独立线程池与 Web 请求线程隔离；告警订阅者异步执行，数据库写入不阻塞每秒控制周期 |
| 配置 | 业务参数（阈值、周期、开关）外部化到配置文件，避免魔法数字散落在代码中 |
| 可观测性 | Actuator 健康检查端点，可接入容器探针或负载均衡 |
| 测试 | JUnit 5 + Mockito，按纯逻辑、服务、接口、持久层、整体装配五个层次组织，共 25 个用例 |
| 容器化 | Docker Compose 管理数据库依赖并完成首次建表；应用提供独立 Dockerfile，环境搭建从"安装 MySQL、建库建表"缩减为一条命令 |

### 代码组织

代码严格按职责分包，包名即架构分层：

- `controller`：接口层，REST 入口与全局错误处理
- `service`：核心业务层，主控板服务、每秒控制的调度入口、温度演化仿真器
- `service/strategy`：调速策略接口及其聚合实现
- `service/event`：告警事件定义与异步订阅者
- `mapper` + `resources/mapper`：数据访问接口与 SQL 映射
- `entity` / `dto` / `domain`：数据库实体、请求与响应对象、业务枚举，三者互不混用
- `exception`：业务语义异常（槽位不存在、模式冲突）
- `config`：可调参数绑定、调度线程池配置
- `init`：启动时的初始板卡播种（幂等）
- `test`：与主代码包结构一一对应的测试代码，测试配置独立，使用内嵌内存数据库

## 三、领域建模

系统的世界里只有三类对象。理解了它们各自持有什么状态、状态按什么规则流转，就理解了整个系统。

### 三类领域对象

| 对象 | 身份 | 持有状态 | 性质 |
|---|---|---|---|
| 风扇板 | 槽位号（90、91 两块） | 当前档位（低 / 中 / 高）、工作模式（手动 / 自动） | **当前状态**：持续存在、可被反复覆写 |
| 业务板 | 槽位号（1–14，共 14 块） | 当前温度 | **当前状态**：每轮控制后被刷新 |
| 告警记录 | 自增流水号 | 越线板卡槽位、越线瞬间温度、发生时间 | **历史事实**：只追加、不修改、不删除 |

"当前状态"与"历史事实"的区分是整个建模的关键：风扇板和业务板回答"现在怎么样"，告警记录回答"什么时候发生过什么"。正因为告警是独立的事实流，它才适合用事件机制异步产生（见下一章观察者模式），而不是和板卡状态塞进同一次更新。

系统启动时播种初始拓扑：两块风扇板处于低速、手动模式；14 块业务板初始温度均为 20℃。播种是幂等的，库里已有数据时不会重置。

### 业务板温度如何变化

每一轮控制周期（默认每秒一轮），每块业务板的温度独立演化：

1. **自然升温**：叠加一个 0 ~ 0.5℃ 的均匀随机增量，模拟业务板持续发热；
2. **散热降温**：再按风扇当前档位减去一个随机量——高速档单块 0 ~ 1.0℃，中速档 0 ~ 0.3℃，低速档 0 ~ 0.1℃；
3. **物理钳位**：结果限制在 10℃ ~ 100℃ 之间，任何随机组合都不会产生越界温度。

### 风扇档位如何决策

- **单板建议**：温度 ≤ 35℃ 建议低速；35℃ < 温度 ≤ 60℃ 建议中速；温度 > 60℃ 建议高速；
- **全局聚合**：取所有业务板建议的**最高档**——任一块需要高速则两块风扇板都跑高速，否则任一块需要中速则中速，全部低温才低速。按散热短板决策，符合机房安全优先的语义；
- **写入约束**：自动决策只允许写入处于自动模式的风扇板；手动模式的板卡完全不受自动控制影响。反过来，自动模式下人工调速请求会被拒绝（返回 409 冲突），只有切回手动模式才能人工指定档位。两条规则共同保证"谁在控制这块板"在任何时刻都没有歧义。

### 告警何时产生

- 阈值默认 75℃，可配置；
- 采用**边沿触发**：只有"上一轮温度 ≤ 阈值、本轮温度 > 阈值"的跨越瞬间才产生一条告警记录。温度持续高于阈值时不会每秒重复记录；温度自然回落到阈值内后，下一次越线才会产生新的一条。因此告警表中的行数等于真实的越线次数，而不是超温持续的秒数。

三类对象在数据库中分别对应 `fan_board`、`business_board`、`alarm_record` 三张表，前两张以槽位号为主键、末者以自增流水号为主键。建表脚本幂等，容器首次初始化和应用重复启动都可以安全执行。

## 四、三个核心设计模式

### 1. 单例模式：全局唯一的主控板

机房里主控板只有一块，所有控制指令必须汇聚到同一个入口，系统中主控板服务的建模与此一致：由 Spring 容器保证整个应用生命周期内只存在一个实例，所有接口请求和定时调度拿到的都是同一个对象。

相比自己在代码里实现单例（私有构造、双重检查锁、volatile 字段），容器托管的做法把"保证唯一"这件事交给了框架：业务代码只写控制逻辑，线程安全由容器初始化机制保证，同时这个唯一实例还能正常接受依赖注入、被统一管理生命周期。

### 2. 观察者模式：温度越线的发布与订阅

上一章把告警建模为独立的"历史事实流"，观察者模式正是它的实现方式：

- 主控板只负责在温度从阈值内跨越到阈值外的一瞬间发布"温度告警事件"，事件里带槽位和当时温度；
- 告警记录订阅者在收到事件后异步落库，写库耗时或失败都不影响主控板继续调速；
- 主控板完全不知道订阅者的存在。将来要增加声光告警、短信通知、推送运维群，只需要新增订阅者，主控板一行代码都不用改——这正是观察者模式"发布方与订阅方解耦、订阅方可动态增减"的价值。

### 3. 策略模式：可替换的调速规则

"所有业务板温度如何汇总成一个风扇档位"是一条独立变化的规则，因此把它从主控板中剥离，定义为调速策略角色：输入全部业务板温度，输出一个目标档位。

当前提供的聚合策略就是上一章描述的"逐块判定、取最高档"。如果以后要换成分区调速、加权平均、结合历史温度的滞回规则，只需新增一个策略实现并替换装配，主控板的控制流程完全不动。变化的部分被隔离在一个类里，不变的部分得到复用。

## 五、设计决策

1. **主控板使用容器单例而非手写单例**。"全局唯一"是需求本身，而保证唯一的机制交给框架容器：消灭手写双重检查锁与 volatile 的复杂度，实例同时获得依赖注入和完整生命周期管理。
2. **一轮控制周期内部严格串行**。温度演化、档位决策、状态落库、告警判断在同一轮调用中按固定顺序完成，从根本上消除"边读温度边改温度"的共享状态竞争，而不是靠加锁去掩盖它。
3. **用数据库条件更新兜底手动与自动的并发冲突**。自动调速的更新语句带"模式必须为自动"的条件，即使应用层判断和落库之间用户恰好切换了模式，数据库也会保证手动板不被自动调速覆盖——并发安全下沉到数据层这一道最终防线。
4. **告警采用边沿触发而非电平触发**。只在温度从阈值下方跨越到上方的瞬间记录一条，持续超温不刷屏；温度自然回落到阈值内后，下次越线才会产生新告警，告警历史真实反映"越线事件"的次数。
5. **告警写库异步化解耦**。越线判断属于每秒控制周期的关键路径，而写历史库不是。发布事件后立即返回，订阅者异步落库，即使告警存储暂时不可用，风扇调速也不受影响。
6. **测试与生产使用不同数据库，但代码零分支**。生产是 MySQL，测试是一次性内存库，切换只发生在配置层：既保证测试零外部依赖、秒级跑完，又不让代码里出现任何"如果是测试环境就怎样"的特殊逻辑。
7. **基础设施容器化、职责单一**。Docker Compose 只负责把数据库这一个有状态依赖跑起来并完成初始化，应用本身无状态，二者独立启停；新人拿到项目的启动成本是一条命令加一个 Maven 目标，而不是安装、配置、建库的一串手工步骤。
